# MD-06. 글로벌화(타임존·다국어·통화) 미적용 — 한국 단일 시장 전제

| 항목 | 내용 |
|------|------|
| 심각도 | MD (Medium) |
| 대상 | 전체 서비스 + 프론트엔드 |
| 상태 | **의도적 미적용** — Roadmap v2.0으로 계획 |
| 결정일 | 2026-08-10 |

## 1. 현재 설계 (한국 단일 시장 전제)

| 축 | 현재 구현 | 근거 |
|----|-----------|------|
| **타임존** | `TimeZone.setDefault(Asia/Seoul)` 명시 고정(`ServiceTimeZone`), `spring.jackson.time-zone: Asia/Seoul` | 단일 시장이므로 서버·DB·표시 타임존을 하나로 통일하는 것이 가장 단순하고 오류가 적다 |
| **날짜 저장** | DB `TIMESTAMP`(타임존 없음) + JPA `LocalDateTime` | 위와 동일 전제. 한 타임존만 쓰면 오프셋 정보가 불필요 |
| **다국어** | 미적용. 화면 문자열·백엔드 예외 메시지 한국어 하드코딩 | i18n 프레임워크 도입 없이 개발 속도 우선 |
| **통화** | `long`(원 단위, 소수점 없음), 프론트 `Intl.NumberFormat('ko-KR', KRW)` | KRW는 최소 단위가 1원이라 정수로 안전하게 표현 가능 |

**핵심**: 타임존은 "모르고 방치"가 아니라 **명시적으로 고정**했다(V1.1-7 매출 통계 리뷰에서 UTC 컨테이너 배포 시 `to` 당일 최대 9시간 누락이 지적되어 KST 고정 + 배포 체크리스트에 반영).

## 2. 왜 지금 하지 않는가

1. **기능이 아니라 아키텍처 변경**이다. v1.1/v1.2의 기능 항목과 성격이 다르며, 규모는 v1.1 잔여 기능(PG결제·마일리지·쿠폰)을 합친 것보다 크다.
2. **어설픈 다국어는 미적용보다 나쁘다.** 화면 일부만 번역된 상태는 완성도를 떨어뜨린다. 상품명·카테고리처럼 **판매자가 입력하는 데이터**까지 다국어화해야 실제로 동작하는데, 이는 데이터 모델 변경을 수반한다.
3. **다국어는 늦게 할수록 비용이 늘지 않는다.** 작업량 = 문자열 수 × 화면 수이므로, 화면이 확정된 뒤 일괄 처리하는 편이 효율적이다. 오히려 먼저 도입하면 이후 모든 신규 기능에 번역 키 관리 부담이 붙는다.
4. **단, 타임존은 반대다.** `LocalDateTime → Instant` 전환은 시간 필드를 쓰는 기능이 늘수록 수정 범위가 커진다 → **다국어보다 우선순위가 높고, 분리해서 먼저 처리**하는 것이 합리적이다(v2.0 내 순서: 타임존 → 통화 → 다국어).

## 3. 글로벌화 시 실제로 바뀌는 것

### 3.1 타임존 (영향도: 높음)
- DB: `TIMESTAMP` → **`TIMESTAMPTZ`**, 기존 데이터는 KST로 해석해 UTC로 변환하는 **마이그레이션 필요**
- 엔티티: `LocalDateTime` → **`Instant`**(UTC 저장), 표시 시점에만 사용자 타임존으로 변환
- 영향 필드: 주문 `createdAt`, 배송상태 변경, 반품 `requestedAt/processedAt/refundedAt`, 알림 `createdAt`, 리뷰, 장바구니, 실패주문 로그
- **집계 정책 재정의**: "7월 매출"이 누구 기준 7월인가 → 일반적으로 **상점(판매자) 기준 타임존 고정**. 통계 API에 타임존 파라미터 또는 상점 설정 필요
- 프론트: 날짜 표시를 사용자 로캘/타임존 기준으로 포맷

### 3.2 다국어 (영향도: 매우 높음)
- **UI 문자열**: `react-i18next` 도입 + 전 화면 문자열 추출(화면 20개+, 수백 개 문자열)
- **백엔드 메시지**: 예외 메시지를 `messages_ko.properties` / `messages_en.properties`로 분리, `Accept-Language` 기반 `MessageSource` 적용. 현재 ProblemDetail `detail`이 한국어 하드코딩
- **콘텐츠 다국어(가장 큼)**: 상품명·설명·카테고리명은 **DB 다국어 테이블**(`product_translation(product_id, locale, name, description)`) 필요. 판매자가 언어별로 입력하는 UI, 미번역 시 폴백 정책, 검색·자동완성도 로캘별 처리 필요
- 이메일 템플릿(임시 비밀번호 등)도 로캘별

### 3.3 통화 (영향도: 높음)
- 현재 `long`(원)은 **소수점 없는 통화 전제**. USD/EUR는 2자리 소수 → `BigDecimal` + **통화 코드(ISO 4217)** + 최소 단위(minor unit) 관리 필요
- 상품 가격을 통화별로 저장할지, 기준 통화 + 환율 변환할지 결정 필요(환율 스냅샷 보관 여부 포함)
- **주문 금액은 결제 시점 통화·환율을 스냅샷**해야 함(사후 환율 변동과 무관하게 이력 보존)
- PG 연동(V1.1-6)도 통화별 지원 범위가 달라짐 → 결제 설계와 함께 결정하는 것이 유리

### 3.4 부수 항목
- 주소 체계(국가별 우편번호·주소 형식), 전화번호 국가코드(현재 `^0\d{1,2}-?\d{3,4}-?\d{4}$`는 한국 전용)
- 배송비·세금(VAT/부가세) 정책, 국가별 법적 고지

## 4. 확장 지점 (지금 남겨둔 것)
- `ServiceTimeZone` 상수 1곳에서 타임존을 관리 → 전환 시 시작점이 명확
- 통계 Service는 기간 파라미터를 받는 구조라 타임존 파라미터 추가가 용이
- 금액은 전 구간 `long` 단일 타입으로 통일 → `BigDecimal` 전환 시 탐색 범위가 명확

## 5. 결론
포트폴리오 범위에서는 **한국 단일 시장 전제를 유지**하고, 글로벌화는 **Roadmap v2.0 별도 트랙**으로 계획한다. "고려하지 않은 것"이 아니라 **"범위를 정하고 확장 경로를 설계해 둔 것"**이 이 문서의 목적이다.
