# 통합 설계 — 결제·할인 기반 규칙 (V1.1-6 / 9 / 10 공통)

> **이 문서의 목적**: 결제(V1.1-6)·마일리지(V1.1-9)·쿠폰(V1.1-10)은 **결제금액 계산이라는 한 지점에서 만난다.**
> 각각 따로 설계하면 적용 순서·적립 기준·취소 원복 규칙이 서로 어긋난다. 기능 설계에 들어가기 전에 **공통 규칙을 먼저 확정**한다.
> 개별 기능 설계 문서(payment-pg.md / coupon.md / mileage.md)는 이 문서의 규칙을 참조하며, 이 문서와 충돌하면 **이 문서가 우선**한다.

## 0. 현황 (변경 대상)
| 항목 | 현재 |
|------|------|
| 주문 금액 | `Order.totalPrice` = **ACTIVE 항목의 `price × quantity` 합**만. 할인 개념 없음 |
| 결제 | **없음**(mock). 주문 생성 즉시 PENDING → 재고 차감 Saga → CONFIRMED |
| 취소 | 항목/주문 단위 취소 시 `recalculateAfterCancel()`로 `totalPrice` 재계산 |
| 반품 | 승인 시 재고 복구 + `processRefund()` **훅만 존재**(mock) |

→ 결제·할인이 들어오면 **"주문 금액" 하나로는 부족**하다. 아래 금액 모델로 확장한다.

---

## 1. 금액 모델 (가장 중요)

주문에 다음 금액을 **모두 스냅샷**한다. 계산 결과만 저장하면 사후 감사·부분취소 시 재구성이 불가능하다.

| 필드 | 의미 | 예 |
|------|------|-----|
| `itemsTotal` | 항목 합계(정가 기준, ACTIVE 항목) | 50,000 |
| `couponDiscount` | 쿠폰 할인액 | 5,000 |
| `mileageUsed` | 마일리지 사용액 | 3,000 |
| `payableAmount` | **실제 결제금액** = `itemsTotal − couponDiscount − mileageUsed` | 42,000 |
| `mileageEarned` | 적립된 마일리지 | 420 |

**불변식**: `payableAmount = itemsTotal − couponDiscount − mileageUsed`, 그리고 `payableAmount >= 0`.

> 기존 `totalPrice`는 `itemsTotal`로 의미를 명확히 하거나 유지하되, **결제금액과 혼동되지 않도록** 이름·용도를 문서와 코드에서 통일한다. 통계(V1.1-7)의 "유효 매출"이 어느 값을 쓸지도 여기서 결정해야 한다 → **§6 참조**.

---

## 2. 적용 순서 (할인 계산)

```
1) itemsTotal        = Σ(ACTIVE 항목 price × quantity)
2) couponDiscount    = 쿠폰 정책 적용(정률/정액, 상한·최소주문금액 검증)
3) 중간금액          = itemsTotal − couponDiscount
4) mileageUsed       = min(요청 사용액, 보유잔액, 중간금액)
5) payableAmount     = 중간금액 − mileageUsed
```

**확정 규칙**
- **쿠폰 먼저, 마일리지 나중.** 정률 쿠폰은 *정가 기준*으로 계산한다(마일리지 차감 후 금액에 %를 적용하면 사용자가 마일리지를 쓸수록 할인이 줄어드는 불합리 발생).
- **마일리지는 중간금액을 초과할 수 없다** — 잔액이 남아도 결제금액 이상은 사용 불가(현금화 방지).
- `payableAmount == 0`이면 **PG 호출을 생략**하고 즉시 결제완료 처리한다(전액 쿠폰/마일리지 결제). 이 경로도 주문 확정·적립이 동일하게 동작해야 한다.
- **배송비는 이번 범위 밖**(현재 미구현). 도입 시 "할인은 상품금액에만 적용, 배송비는 별도"를 기본으로 한다.

## 3. 적립 규칙 (마일리지)

### 3.1 적립 기준
- **적립 기준 = `payableAmount`(실결제액)**, 정가 아님.
  - 근거: 정가 기준으로 적립하면 쿠폰·마일리지로 깎인 금액에 다시 적립되어 **할인이 중복 지급**된다.
  - 마일리지로 결제한 부분은 적립 대상이 아니다(이미 혜택을 쓴 금액).
- 적립률은 정책값(기본 1%), **원 단위 절사**(소수점 버림).

### 3.2 적립 시점 = **구매확정** (주문 확정 아님)
> **이 결정이 회수 문제를 근본적으로 없앤다.**

```
배송완료 ──(사용자 "구매확정" 버튼 or 7일 경과 자동확정)──> 구매확정 ──> 마일리지 적립
             └───────────── 이 구간에서만 반품 가능 ─────────────┘
```

- 주문 확정(CONFIRMED) 시점에 적립하면 **"적립 → 사용 → 반품 → 회수 불가"** 경로가 열린다. 구매확정 후 적립하면 **반품 가능 기간이 끝난 뒤 적립**되므로 회수가 사실상 발생하지 않는다.
- **자동확정**: 배송완료(DELIVERED) 후 **7일** 경과 시 스케줄러가 자동 확정(국내 주요 쇼핑몰 표준). 기간은 정책값.
- **구매확정 = 반품 불가.** 반품 자격에 "구매확정 전" 조건을 추가한다. 확정 버튼에는 "확정 시 반품·교환이 어렵습니다" 경고를 노출한다.
  - 법정 청약철회(전자상거래법)는 시스템 밖 CS 영역으로 처리 — 범위 밖.
- **연쇄 효과**: 리뷰 작성 자격(§3.4), 판매자 정산 기준일(V1.2-7)도 구매확정에 연결된다.

### 3.3 미수금(clawback pending) — 회수 실패 처리
회수가 필요한데 잔액이 부족한 경우(주로 CS 처리된 예외 반품, 어뷰징 리뷰 삭제):

- **잔액을 음수로 만들지 않는다.** 회수 가능한 만큼만 차감하고, 부족분은 **미수금**으로 기록한다.
  - 근거: 음수 잔액은 다음 주문에서 예상치 못한 결제 실패를 만들고 CS 비용이 크다.
- **상계 방식 = 적립 시점 즉시 상계.** 이후 적립이 발생하면 지급 직전에 미수금을 먼저 차감한다.
  ```
  회수 필요 500P, 잔액 0P  → 잔액 0 유지 + 미수금 500P
  이후 300P 적립 발생      → 사용자 지급 0P, 미수금 200P
  이후 200P 적립 발생      → 사용자 지급 0P, 미수금 0P (해소)
  ```
- **배치를 쓰지 않는다.** 일배치로 상계하면 배치 주기 사이에 사용자가 적립금을 써버려 미수금이 다시 남는다. 적립 지급 직전 상계가 새는 구멍이 없고 스케줄러도 불필요하다.
- **상계 발생 시 사용자에게 알림**(V1.1-4 알림 인프라 재사용). 적립이 들어오지 않은 이유를 알 수 있어야 CS 문의를 줄인다. 알림 타입 `MILEAGE_OFFSET`.

### 3.4 사용 제약 (관리자 변경 가능)
- **최소 사용금액**: 기본 **1,000P** 이상부터 사용 가능
- **사용 단위**: 기본 **100P** 단위
- 두 값은 **정책 테이블에 저장**하고 **관리자 화면에서 변경 가능**하게 한다(재배포 없이 조정). 적립률·자동확정 기간도 동일하게 관리한다.
  - `mileage_policy`(earnRate, minUseAmount, useUnit, autoConfirmDays, updatedBy, updatedAt) — 단일 행 정책 테이블
- **유효기간은 범위 밖**. 최소 사용금액을 두면 소액 잔액이 영구히 남아 부채로 쌓이므로, 도입 시 유효기간(예 1년)을 부채 정리 수단으로 함께 설계한다 — 이 트레이드오프를 문서에 남긴다.

## 4. 취소·반품 시 원복 (가장 복잡 — 규칙을 여기서 못 박는다)

### 4.1 원칙
> **"쓴 것은 돌려주고, 받은 것은 회수한다. 단, 이미 소진된 혜택은 음수로 만들지 않는다."**

| 상황 | 마일리지 사용분 | 마일리지 적립분 | 쿠폰 | PG 결제 |
|------|----------------|----------------|------|---------|
| **전체 취소**(PENDING) | 전액 환급 | 미적립(확정 전) | **복구**(재사용 가능) | 미승인 → 취소 |
| **전체 취소**(CONFIRMED) | 전액 환급 | **전액 회수** | **복구** | 전액 환불 |
| **부분 취소/반품** | **비례 환급**(§4.2) | **비례 회수** | **복구 안 함**(§4.3) | 비례 환불 |

### 4.2 부분 취소 시 비례 배분
취소된 항목 금액 비율만큼 할인·적립도 비례 조정한다.

```
취소비율 = 취소항목 정가합계 / itemsTotal
환급 마일리지 = floor(mileageUsed × 취소비율)
회수 마일리지 = floor(mileageEarned × 취소비율)
PG 환불액   = payableAmount − (남은 항목 기준 재계산 payable)
```
- **端수는 사용자에게 유리하게**(환급은 올림, 회수는 내림) 처리하여 사용자 불이익을 만들지 않는다.
- 여러 번 부분취소가 일어나도 **누적 환급액이 원래 사용액을 넘지 않도록** 이미 환급한 금액을 추적한다.

### 4.3 쿠폰은 부분취소 시 복구하지 않는다
- 1회용 쿠폰을 부분취소마다 복구하면 **할인만 챙기고 일부만 남기는 악용**이 가능하다.
- **전체 취소일 때만 복구**한다. 부분취소 시에는 쿠폰 할인액을 남은 항목에 그대로 유지(즉 재계산 시 `couponDiscount`는 변경하지 않음).
- 예외: 남은 항목이 쿠폰의 **최소주문금액을 못 미치게 되어도 소급 취소하지 않는다**(사용자 불이익 금지).

### 4.4 회수 시 잔액 부족 → 미수금 상계
- **적립 시점을 구매확정으로 옮겼으므로(§3.2) 이 경로는 거의 발생하지 않는다.** 남는 경우는 CS로 처리된 예외 반품, 어뷰징 리뷰 삭제(§4.5) 정도다.
- 처리 방식은 **§3.3 미수금 상계**를 따른다 — 잔액 음수 금지, 부족분은 미수금으로 기록 후 다음 적립에서 즉시 상계, 상계 시 사용자 알림.

### 4.5 리뷰 적립 회수 (리뷰 정책 연계)
리뷰 삭제 시 적립을 회수할지는 **삭제 사유에 따라 나눈다**.

| 삭제 사유 | 적립 회수 | 근거 |
|-----------|-----------|------|
| **어뷰징·규정위반**(도배·광고·무관한 내용·가짜 사진) | **회수** | 부정 취득이므로 환수가 정당 |
| **단순 분쟁·판매자 요청**(표현이 거칠다 등) | **회수 안 함** | 무조건 회수하면 판매자가 낮은 별점 리뷰를 신고해 작성자에게 불이익을 주는 **무기**가 된다 |

- 회수 시에도 §3.3 미수금 규칙을 그대로 적용한다.

## 5. 주문 상태 흐름 (결제 도입 후)

**결정(§11-2)**: 주문을 `PAYMENT_PENDING`으로 **먼저 생성**한 뒤 결제를 승인한다.

```
주문 생성(PAYMENT_PENDING) ──승인──> PENDING ──재고차감 성공──> CONFIRMED ──배송──> DELIVERED
   │                                   │                                          │
   ├─승인 실패/이탈──> CANCELLED         └─재고 실패──> CANCELLED(+환불)              │
   └─30분 방치──> 만료(스케줄러)                                                     ▼
                                                     (확정 버튼 or 7일 자동확정)
                                                                                   │
                                                                                   ▼
                                                              구매확정 ──> 적립 · 리뷰 작성 가능
```

- **선생성 이유**: "승인은 됐는데 주문 생성 실패"(돈은 빠졌는데 주문 없음)를 원천 차단. 모든 결제 시도가 주문으로 추적되고, 웹훅이 늦게 와도 주문에 매칭된다.
- `payableAmount == 0`이면 승인 단계를 건너뛰고 곧바로 `PENDING`으로 전이한다(§2, §11-3).

- **구매확정 전까지만 반품 가능.** 확정 후에는 반품 불가(§3.2).
- 자동확정 스케줄러: 배송완료 후 7일(정책값) 경과 주문을 일괄 확정. 다중 인스턴스 대비 **중복 실행 방지**(락 또는 조건부 UPDATE) 필요.

- **PG 승인 후에 주문을 만든다**(또는 주문을 PAYMENT_PENDING으로 만들고 승인 후 PENDING 전이). 승인 전 재고를 차감하지 않는다.
- **재고 차감 실패 시 이미 승인된 결제를 환불**해야 한다 → 기존 보상 Saga에 **결제 취소 단계 추가**.
- 쿠폰·마일리지는 **결제 시도 시점에 선점(hold)**, 최종 확정 시 확정 처리, 실패 시 해제. 선점 없이 진행하면 동시 주문에서 이중 사용이 가능하다.

### 5.1 Saga 보상 흐름 (확장)
| 단계 | 실패 시 보상 |
|------|-------------|
| 쿠폰·마일리지 선점 | 선점 해제 |
| PG 결제 승인 | 승인 취소(void) + 선점 해제 |
| 재고 차감 | **PG 환불** + 마일리지 환급 + 쿠폰 복구 + 주문 CANCELLED |

## 5.2 리뷰 정책 개편 (V1.1-1 기존 구현 변경)

구매확정 도입과 리뷰 적립이 붙으면서 **기존 리뷰 구현을 바꿔야 한다.**

| 항목 | 기존 | 변경 |
|------|------|------|
| 작성 자격 | CONFIRMED 주문이면 가능 | **구매확정된 주문항목만** |
| 단위 | 1인 1상품 1리뷰 (`UNIQUE(user_id, product_id)`) | **주문항목당 1리뷰** (`UNIQUE(order_item_id)`) |
| 사진 | 없음 | **0~5장 첨부**(MinIO 업로드·매직넘버 검증 재사용) |
| 삭제 | 본인 삭제 가능 | **자가삭제 불가**, 관리자만 삭제 |
| 적립 | 없음 | 텍스트 기본 + **사진 첨부 시 추가 적립** |

**왜 주문항목 단위인가**: 1상품 1리뷰를 유지하면 **재구매해도 리뷰를 못 쓰고 적립도 못 받아** 재구매 유인이 사라진다. 주문항목 단위로 바꾸면 재구매마다 리뷰·적립이 가능하고 "어느 주문의 리뷰인지" 추적된다.

**세부 규칙**
- 구성: 별점 1~5(필수) + 내용(**최소 10자** 필수) + 사진 0~5장(선택)
- **작성 기한 없음. 단 적립은 구매확정 후 30일 이내**에 작성한 리뷰만.
  - 근거: 리뷰 자체를 막으면 상품 정보가 줄어 플랫폼이 손해다. 적립만 기한을 둔다.
- **적립은 주문항목당 1회.** 수정해도 재지급 없음, 삭제 후 재작성도 재지급 없음(어뷰징 차단).
- 자가삭제 불가 → "적립받고 삭제" 경로가 원천 차단된다.
- 포토 적립 어뷰징 방어: 이미지 실제 첨부·매직넘버 검증(기존 로직 재사용), 최소 글자수, 주문항목당 1회 제한.
- **판매자 신고 기능은 v1.2로 이관.** 지금은 관리자 직접 삭제만 구현하고, 삭제 시 사유(어뷰징/단순분쟁)를 선택해 §4.5 회수 여부를 결정한다.

## 6. 매출 통계와의 정합 (V1.1-7 영향)

현재 통계의 "유효 매출"은 **ACTIVE 항목의 정가 합계**다. 할인이 도입되면 **정가 매출과 실매출이 갈라진다.**

**결정**: 통계에 두 값을 **분리 제공**한다.
- `grossRevenue` = 정가 기준(현재 값, 상품 판매력 지표)
- `netRevenue` = **실결제액 기준**(`payableAmount` 합, 실제 유입 금액)
- 할인 총액(`couponDiscount + mileageUsed`)도 지표로 노출 → 프로모션 효과 측정

> 통계 구현 시 이 분리를 반영해야 하며, 기존 `유효 매출` 라벨은 `총 상품매출(정가)`로 명확히 바꾼다.

## 7. 데이터 모델 개요 (상세는 개별 설계 문서)

| 대상 | 저장 |
|------|------|
| 주문 금액 | `orders`에 `items_total`, `coupon_discount`, `mileage_used`, `payable_amount`, `mileage_earned` 컬럼 추가 |
| 결제 | `payment`(orderId, pgProvider, pgTransactionId, amount, status, approvedAt, canceledAt) |
| 쿠폰 | `coupon`(정의) / `user_coupon`(보유·사용, 상태 HELD/USED/AVAILABLE) |
| 마일리지 | `mileage_ledger`(userId, orderId, amount, type=EARN/USE/REFUND/CLAWBACK/**OFFSET**, createdAt) — **잔액은 원장 합계로 계산**하거나 별도 잔액 테이블 + 원장 병행 |
| 마일리지 미수금 | `mileage_pending_clawback`(userId, amount, reason, createdAt, resolvedAt) 또는 잔액 테이블에 `pendingClawback` 컬럼 — §3.3 상계 대상 |
| 마일리지 정책 | `mileage_policy`(earnRate, minUseAmount, useUnit, autoConfirmDays, reviewTextPoint, reviewPhotoPoint, updatedBy, updatedAt) — **단일 행**, 관리자 화면에서 변경 |
| 구매확정 | `orders`에 `purchase_confirmed_at` 컬럼(또는 상태값) |
| 리뷰 | `review`에 `order_item_id` 추가(UNIQUE 변경) + `review_image`(reviewId, imageUrl, sortOrder) |

- **마일리지는 원장(ledger) 방식**으로 한다. 잔액만 두면 취소·회수 이력 추적이 불가능해 CS·감사에서 막힌다.
- 모든 금액은 `long`(원 단위) 유지 — 통화 다중화는 v2.0(글로벌화) 범위.

## 8. 동시성·정합성

- **마일리지 사용**: 잔액 초과 방지를 위해 원장 삽입 시 **잔액 재검증 + 낙관적 락 또는 조건부 UPDATE**. 동시 요청에서 잔액이 음수가 되면 안 된다.
- **쿠폰 사용**: `user_coupon` 상태 전이(AVAILABLE → HELD → USED)를 **조건부 UPDATE**(WHERE status='AVAILABLE')로 원자 처리. 이중 사용 시 두 번째는 실패.
- **PG 승인 멱등**: 동일 주문 재승인 방지(주문당 승인 1건), 웹훅 재전송 대비 `pgTransactionId` 기준 멱등 처리.
- **결제 웹훅 검증**: 서명 검증 필수, 키·시크릿은 env(로그 마스킹).

## 9. 구현 순서 (권장)

1. **금액 모델 확장** — `orders`에 금액 컬럼 추가, 기존 주문은 `items_total = totalPrice, payable = totalPrice`로 마이그레이션
2. **구매확정** — 확정 버튼 + 7일 자동확정 스케줄러, 반품 자격에 "확정 전" 조건 추가
   - 마일리지 적립 시점의 전제이므로 결제보다 먼저 또는 병행. 단독으로도 가치가 있다(주문 라이프사이클 완성).
3. **V1.1-6 PG 결제** — 결제 뼈대·상태 흐름·Saga 보상 확장(할인 0인 상태로 먼저 동작시킴)
4. **V1.1-10 쿠폰** — 할인 1종 추가, 선점/확정/복구
5. **V1.1-9 마일리지** — 사용·적립·미수금 상계·정책 관리 화면(규칙이 가장 많아 마지막)
6. **리뷰 개편(§5.2)** — 주문항목 단위 전환·사진 첨부·자가삭제 제거·적립 연동
   - 마일리지 적립과 엮이므로 5 이후. 주문항목 단위 전환은 **기존 데이터 마이그레이션** 필요(현 리뷰에 order_item_id 채우기 — 매칭 불가한 과거 리뷰 처리 방침 결정 필요).

> 순서 근거: 결제 뼈대를 먼저 세우고 할인을 얹어야 취소·환불 경로를 한 번만 만든다. 반대로 하면 mock 결제 위에 할인을 만들고 PG 도입 시 재작업하게 된다.

## 11. 확정 사항 (2026-08-18 결정)

| # | 항목 | 결정 | 근거 |
|---|------|------|------|
| 1 | **PG 제공사** | **토스페이먼츠 샌드박스** | 테스트키 즉시 발급·사업자등록 불필요·문서 품질. 샌드박스 무료(라이브 전환 시에만 수수료). 테스트 카드로 승인/취소/부분취소 전 흐름 검증 가능 |
| 2 | **주문 생성 시점** | **PAYMENT_PENDING 주문 선생성 → 승인 → PENDING** | "승인은 됐는데 주문 생성 실패"(돈은 빠졌는데 주문 없음)가 가장 위험한 시나리오. 선생성하면 **모든 결제 시도가 주문으로 추적**되고 웹훅 지연 시에도 주문 매칭이 가능하다 |
| 3 | **전액 할인 결제(payable=0)** | **PG 호출 생략, 즉시 결제완료** | 대부분 PG가 0원 결제를 거부한다. 내부 `payment` 레코드는 남기되 PG 왕복은 하지 않는다 |
| 4 | **기존 리뷰 마이그레이션** | **매칭 시도 후 실패분은 `order_item_id` NULL 허용** | 데이터 손실 없이 전환. 매칭 실패한 과거 리뷰는 **레거시 리뷰**로 두어 수정·삭제만 가능하고 적립 대상에서 제외 |

### 11.1 결정에 따른 파생 작업
- **(2번 파생) 미완료 주문 정리** — `PAYMENT_PENDING` 상태로 방치된 주문을 일정 시간(예 30분) 후 만료 처리한다. **구매확정 자동확정 스케줄러에 함께 태워** 스케줄러를 추가로 늘리지 않는다.
- **(3번 파생) 0원 결제 경로 테스트 필수** — 주문 확정·적립·취소·환불 흐름이 **PG 결제 경로와 동일하게** 동작하는지 별도 테스트. 결제를 건너뛰는 분기라 버그가 숨기 쉽다.
- **(4번 파생) 레거시 리뷰 취급 명시** — 목록·평균 별점 집계에는 포함하되, 적립·주문항목 연계 기능에서는 제외한다.
- **(1번 파생) 키 관리** — 토스 테스트 시크릿키는 **env 주입**, 로그 마스킹. 배포 체크리스트에 추가.
- **(2번 파생) 결제 정합성 보강** — 승인 타임아웃 재조회·확정 실패 보상·미결(UNKNOWN) 상태와 남은 리스크는 [payment-pg-integrity.md](payment-pg-integrity.md) 참조.
