# PG 결제 정합성 보강 (코드리뷰 대응, V1.1-6)

`feature/payment-pg` 코드리뷰(2026-08-19)의 CRITICAL 2 / HIGH 4 / MEDIUM 8 대응 결과와 **남은 리스크**를 정리한다.
돈이 오가는 경로이므로 "우리가 모르는 상태"를 만들지 않는 것이 1순위 원칙이다.

---

## 1. 결제 상태 모델 (변경점)

| 상태 | 의미 | 만료 대상 | 재결제 | 환불·조회 |
|---|---|---|---|---|
| `READY` | 승인 요청 직전(PG 왕복 중) | **제외** | 차단(진행 중) | 대상 아님 |
| `APPROVED` | PG 승인 완료 | 해당 없음 | 차단 | 대상 |
| `CANCELED` | 전액 취소·환불 완료 | 해당 없음 | 차단 | 완료 |
| `FAILED` | PG 거절·고아 결제 정리 | 영향 없음 | **허용** | 제외 |
| `UNKNOWN` (신규) | 통신 실패 후 재조회로도 판정 불가 | **제외** | 차단 | **대상(운영 정산)** |

- `UNKNOWN` 은 "출금됐을 수 있는" 상태다. `FAILED` 로 덮으면 `findActiveByOrderId` 에서 제외되어 환불 경로가
  영구히 사라지므로(리뷰 C-01) 상태를 남기고 실패주문 대장(`failed_order_log`)에 기록한다.
- 진행 중·미확정(`READY`/`UNKNOWN`) 결제가 있는 주문은 **만료(자동취소) 대상에서 제외**한다 — PG 왕복 중에
  주문이 취소되면 승인된 돈이 추적 불가가 된다(리뷰 C-02).

## 2. 승인 실패의 3분기 (C-01)

| 상황 | 판정 | 처리 | 응답 |
|---|---|---|---|
| PG 4xx 거절(`HttpStatusCodeException`) | 확정 실패 | 결제 `FAILED` + 주문 `CANCELLED` | 400 |
| 응답 미수신(타임아웃·연결 실패) | **미확정** | `GET /v1/payments/orders/{pgOrderId}` 재조회 | 아래 |
| 재조회 = `DONE` | 승인됨 | 정상 확정(주문 `PENDING`, 재고 Saga 시작) | 200 |
| 재조회 = 없음(404)·`ABORTED`/`EXPIRED`/`CANCELED` | 미승인 확정 | 결제 `FAILED` + 주문 `CANCELLED` | 502 |
| 재조회 = `IN_PROGRESS`/`WAITING_FOR_DEPOSIT` 또는 재조회 실패 | 판정 불가 | 결제 `UNKNOWN` + 대장 기록 + ERROR 로그 | 502 |

재조회 키(`pg_order_id`)는 승인 준비 시점에 결제 레코드에 저장한다 — 시도별 주문번호(§4)를 서버가
재생성할 수 없기 때문이다.

## 3. 승인 후 확정 실패 보상 (C-02)

`markApproved` 트랜잭션이 실패하는 모든 경로(만료 경쟁, 응답 대조 실패, DB 오류)에서:

1. 승인 금액을 **즉시 PG 취소**(멱등키 `PAYCMP-{결제id}`) → 성공 시 결제 `FAILED` + 주문 취소
2. 취소까지 실패하면 결제 `UNKNOWN` + 대장 기록(수동 환불 대상)

추가로 고아 `READY` 가 부분 유니크 인덱스(`uq_payment_order_active`)를 점유해 **재결제가 409 로 영구 차단**되는
문제를 두 지점에서 푼다.

- 승인 요청 시: 오래된(기본 3분) 진행 중 결제를 재조회로 정리 → 미승인이면 결제만 `FAILED`(주문은 결제 대기 유지)
- 5분 주기 스케줄러(`reconcileInFlightPayments`): 프로세스 종료로 남은 결제를 같은 규칙으로 회수

## 4. 시도별 PG 주문번호 (M-05)

`ORD-{주문id 8자리}-{임의 접미사}` — 결제 실패 후 재시도에서 같은 주문번호를 재사용하면 토스가 거부할 수 있다.
서버는 값을 재생성하지 않고 **규칙·주문 id 일치만 검증**한 뒤 저장해 승인·재조회에 사용한다
(`PgOrderId.requireForOrder`). 프론트는 `newPgOrderId()` 로 시도마다 새로 만든다.

## 5. 취소·환불 정합성 (H-01, H-02, M-06)

- **멱등키**(`PAYCNL-{결제id}-{취소 직전 누적 취소액}`): PG 취소 성공 후 우리 커밋이 실패해도 재시도가 같은 키로
  나가 이중 환불이 걸러진다. 회차가 바뀌면 키도 바뀌어 정상 부분취소는 막지 않는다.
- **비관적 락**(`findActiveByOrderIdForUpdate`) + **`@Version`**: 동시 부분환불의 갱신 유실(초과환불)을 막는다.
  낙관적 락 충돌은 기존 핸들러가 409 로 매핑한다.
- **0원 결제**: 취소 금액이 0이어도 상태를 `CANCELED` 로 전이한다(주문 취소인데 결제만 `APPROVED` 로 남는 불일치 제거).

## 6. 미결 가시성 (H-04)

환불 실패·결과 미확정은 `PaymentIncidentService.record()` 가 **REQUIRES_NEW** 로 기록한다.
호출부(Saga 보상·반품 승인) 트랜잭션이 롤백되어도 기록은 남고, 관리자 실패주문 조회 API로 노출된다.
환불 실패 예외는 그대로 올려 기존 재시도(Kafka 2회 → DLT)·409/502 응답 동작을 유지한다.

## 7. 남은 리스크 (미구현 — 후속 작업)

- **[M-08] PG 웹훅 미구현**: 토스 측 상태 변화(가상계좌 입금, 관리자 콘솔 취소, 승인 지연 완료)를 받는
  엔드포인트가 없다. 현재 복구 수단은 **폴링(5분 주기 재조회)** 과 운영자 수동 처리뿐이다.
  → 웹훅(`POST /api/v1/payments/webhook`, 서명 검증 + 멱등 처리) 도입 시 `UNKNOWN` 해소가 즉시화된다.
- **가상계좌 미지원**: 응답 `status=DONE` 만 승인으로 확정한다. 입금대기(`WAITING_FOR_DEPOSIT`)는 확정하지 않고
  보상 취소하므로, 결제위젯에서 가상계좌를 노출하지 않도록 상점 설정을 유지해야 한다(노출되면 사용자 실패 경험).
- **취소 시 PG 호출이 트랜잭션 안**: 멱등키로 이중 환불은 막았지만 HTTP 왕복(최대 13초) 동안 결제 행 락과
  DB 커넥션을 점유한다. 환불 빈도가 낮아 현재는 수용하고, 아웃박스·재시도 큐 도입 시 트랜잭션 밖으로 뺀다.
- **`UNKNOWN` 자동 해소 한계**: 회수 스케줄러는 오래된 건부터(`created_at asc`) 배치 상한만큼 처리하므로
  영구 미해소 건이 배치 앞자리를 계속 차지할 수 있다. 웹훅 도입 또는 회수 제외 플래그로 보완한다.
